# 安全模型

RelaxKonOS 不重建一套身份与权限体系，而是**把身份和文件权限委托给宿主操作系统**。

## 三条主线

### 1. 身份委托宿主

- Windows：原生 `LogonUser` API，支持本地账户与域账户
- Linux：PAM + NSS
- RelaxKonOS 在宿主确认凭据后签发自己的令牌，**从不保存密码**

### 2. 权限沿用宿主

- 文件操作以登录用户在宿主 OS 上的身份执行
- 没有独立的 ACL 层
- 越权请求由宿主 OS 直接拒绝

### 3. 提权隔离

- 特权操作通过专用 Helper 进程执行
- 契约窄且经过审计
- 危险操作需要显式确认
- 宿主已有机制（sudo、UFW、systemd）时优先复用

## 两层权限必须同时成立

面向宿主的管理功能（[Docker 管理器](/docs/zh-CN/latest/apps/docker)、[代理管理器](/docs/zh-CN/latest/apps/proxy-manager)、[Web Server 管理器](/docs/zh-CN/latest/apps/web-server-manager)、[证书管理器](/docs/zh-CN/latest/apps/certificate-manager)）同时受两层约束：

```text
RelaxKonOS 授权（角色 / 权限 / 已登录会话）
              +
宿主 OS 提权（服务账户权限、特权助手）
```

即使某个组件已经以高权限身份运行，也**不代表任意 RelaxKonOS 用户都可以控制它**。反过来，用户有权限也不代表服务端有宿主特权可用。

## 特权助手的边界

- 服务端**不以 root 或管理员身份运行**，需要宿主特权的操作全部转交助手。
- 助手只接受**固定的、强类型**的动作，不提供「以 root 执行任意命令」一类的通用入口，也不接受任意可执行文件与参数。
- 安装时写入的策略文件决定服务账户能做什么；助手目录与策略文件对该账户不可写。
- 日常启停**不应反复触发提权**：安装、授权与特权动作的定义在首次完成，之后的常规开关不再需要用户审批。

## 宿主授权的后果是显式的

- 需要宿主特权的能力**默认是关闭的**。典型例子是 Docker：守护进程套接字的控制权接近 root 权限，因此部署时不会自动授予，必须在安装时显式选择（见[安装](/docs/zh-CN/latest/getting-started/installation)）。
- 权限不足时，功能返回**稳定问题码**并说明原因，界面提示以更高权限重新部署或启动，而不是静默失败。
- 助手缺失、被卸载或调用被拒绝时，相关功能以问题码失败；**运行中的工作负载不会被中断**，已保存的配置也不会被回滚，可修复后重试。
- 客户端**只显示本地化说明**：不收集 sudo、管理员或服务账户口令，也不把接口变成任意命令的提权通道。

## 分层防护

| 层次 | 措施 |
| --- | --- |
| 传输 | HTTPS、JWT |
| 协议 | 显式契约、输入校验 |
| 服务端 | 路径规范化、目录穿越防护、统一错误处理 |
| 执行 | 结构化参数而非 shell 拼接、危险操作二次确认、操作审计 |
| 渲染 | Markdown 转义，默认不信任 HTML |

## 秘密与日志

- 密码、私钥、账户密钥、控制密钥、订阅地址与代理口令**不进入日志、审计与错误详情**。
- 面向操作者例外：代理地址这类需要回填的字段会原样返回，否则表单往返一次就会把真实凭据改写成掩码；此时掩码只作用于面向读者的日志与诊断。
- 需要存储的秘密以服务端数据保护机制加密，接口只上报版本或引用。
