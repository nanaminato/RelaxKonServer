# Docker マネージャー

Docker マネージャー（RemoteDocker）は、デスクトップから**サーバーホスト**の Docker Engine を操作します。

管理対象は**ローカルの単一エンジンのみ**です。クライアントは Docker ソケットへ直接接続せず、Docker の資格情報も保存せず、デーモンの API をネットワークへ公開しません。

## 機能

- エンジン状態の検出とインストールガイダンス
- コンテナー：表示、起動、停止、再起動
- イメージ：一覧と取得
- スタック：Compose の検証、デプロイ、停止
- ネットワークとボリューム：表示と管理
- ネットワークプロキシー：デーモン層とビルド層の外向きプロキシー
- イメージミラー：ユーザーごとに設定する Docker Hub 互換レジストリー

## 実装

サーバーは `IDockerEngineService` を通じて `docker` CLI を呼び出し、`IDockerComposeService` で Compose を処理します。エンドポイントは `/api/v1.0/docker/*` です。

## イメージミラー

イメージミラーは **Docker マネージャーのミラーページ**で RelaxKonOS アカウントごとに設定し、**ホストのグローバルな `daemon.json` には書き込みません**。

- HTTPS かつ Docker Hub 互換のレジストリーホストを複数保持し、そのうち一つまたは「既定」を選択できます。
- 既定では取得をそのまま実行し、Docker が自身の既定レジストリーを使います。
- ミラーを選択すると、サーバーは Docker Hub の参照をそのミラーへ書き換えてから Docker CLI を呼び出します。
- すでにレジストリーを明示しているイメージ（組織名を伴うサードパーティーイメージなど）は書き換えません。Docker Hub ミラーへ誤って送信されることを防ぎます。
- 選択はサーバーに保存され、**ユーザーごと**です。ある利用者の選択が別の利用者のミラーを置き換えることはありません。

## ネットワークプロキシー

プロキシー経由でしか外部へ出られない環境では、Docker は**互いに独立した二つの**プロキシー設定を必要とし、それぞれ異なるホスト機構を使います。そのため状態は層ごとに報告し、「プロキシー有効」という一つのスイッチへまとめません。

| 層 | 対象 |
| --- | --- |
| デーモン層 | デーモン自身の外向き通信（イメージ取得など） |
| ビルド層 | ビルド中の外向き通信 |

- プロキシーの取得元は、手動で入力したアドレスか、内蔵プロキシーランタイムの待ち受けポートです。内蔵の場合は先に到達性を確認し、到達できなければ失敗として扱い、誰も待ち受けていないポートへデーモンを向けることはありません。
- ビルド層はプロキシー値を子プロセスの環境変数で渡すため、**コマンドラインには現れず**、同じホストの他の利用者がプロセス一覧から資格情報付きアドレスを読むことはできません。
- プロキシーアドレスにはユーザー名とパスワードが埋め込まれる場合があります。保存時は暗号化し、操作者向けの画面では値をそのまま返します（そうしないとフォームを経由した保存で実資格情報が伏せ字に書き換わります）。ログ、監査、診断は常にマスクします。
- デーモン層は**ホスト全体**の設定です。Docker デーモンはワークスペースではなくマシンに属するため、最後に権限をもって書き込んだ利用者の選択が有効になります。
- デーモン層のプロキシーを有効化または削除すると Docker が再起動し、実行中のコンテナーが中断されるため、送信前に確認を求めます。
- 同じ設定は[設定](/docs/ja-JP/latest/apps/settings)の「ネットワーク」カテゴリーからも変更できます。二か所は同一の設定です。

## エンジンのライフサイクル

Docker エンジン全体の起動、停止、再起動は**ホスト単位の操作**で、そのマシン上のすべてのコンテナーを中断するため、コンテナー単位の操作とは分離しており、停止と再起動には明示的な確認が必要です。

これらの操作は現在の実行状態のみを変えます。自動起動の有効化や無効化は行わず、ホスト上の他の設定ファイルも変更しません。

## 権限とセキュリティ

- 操作はホスト OS 上のサービスプロセス ID で実行されます
- 変更操作にはホストの権限（`docker` グループや root など）が必要です
- **Docker アクセスは既定で無効**です。デーモンソケットの制御権は root 権限に近いため、導入時にサービスアカウントを自動でグループへ追加せず、インストール時に明示的に選択します（[インストール](/docs/ja-JP/latest/getting-started/installation)を参照）
- 独自の資格情報ストアは持ち込みません。レジストリー資格情報は参照のみを保存します
- 削除、強制停止、特権コンテナー、Docker ソケットのマウントには二度目の確認が必要です

## プラットフォーム差

| プラットフォーム | 説明 |
| --- | --- |
| Ubuntu | ローカルの Unix ソケットで管理します。デーモン層のプロキシーは systemd の drop-in として書き込み、サービス再起動が必要です |
| Windows 10/11 | ローカルの名前付きパイプで管理します。Docker が利用できない場合、状態ボタンが内蔵ガイダンスを開きます：仮想化の確認、Docker Desktop の導入と起動、バックエンドの選択、Linux コンテナーモードの確認 |
| Windows Server | 導入済みで能力検出に合格したランタイムのみを管理し、**自動導入は行いません** |

Windows デスクトップの経路は開発、個人のセルフホスト、検証に適します。無人運用や本番は専用の Linux ホストを優先してください。

## 既知の制限

- ローカルの単一エンジンのみを管理し、コンテナーオーケストレーションのクラスター、マルチノードプロキシー、リモートデーモン API は実装していません。
- インストール、スタック履歴の永続化、コンテナーターミナル、ストリーミングのリソース統計は設計段階で、画面は利用可能であると主張しません。
- 本アプリは**管理者が使う単一インスタンスのツール**として設計されています。現行の認可はサインイン済み利用者を境界とし、共有導入向けのサーバー側 Docker 読み書きロール分離はありません。マルチテナントのコンテナー制御面として公開せず、信頼できない利用者へサインイン情報を配布しないでください。
