# 更新・削除・保守

導入済み Server の手順です。リモートは信頼済み SSH からサーバーセンターへ、Windows 10/11 本機は[本機管理](/docs/ja-JP/latest/getting-started/windows)へ進みます。既存状態を読んでから操作を選び、原因調査の代わりに再導入しないでください。

## 1. 対象確認と保守の準備

1. 正しいホストで事前検査・状態を更新し、識別子、モード、現在版、プログラム／データディレクトリ、ポート、正常性を確認します。
2. 更新・修復・回退はサービスを再起動してクライアントを切断する場合があるため、利用者に知らせます。復旧可能な SSH または本機管理経路を残します。
3. 重要ファイル、設定、データベースをバックアップし、読み取り可能か確認します。プログラム回退でデータやスキーマが戻るとは限りません。
4. 未完了操作と結果を先に確認し、同じインストールに複数の保守操作を同時送信しません。

| 管理データを永久削除 | データ削除を伴う削除 | プログラム回退では取り消せません |

## 2. Server の更新

1. 導入済みホストで導入／更新ウィザードを開き、既存環境として認識しているか確認します。
2. [リモート導入](/docs/ja-JP/latest/getting-started/remote-installation)に従い、公式、ローカル ZIP、ホスト ZIP、HTTPS を選び、モード、アーキテクチャ、対象版、摘要を確認します。
3. 識別子とディレクトリを確認します。更新は記録済みの配置と構成を使い、通常は TLS を保持して新証明書を自動生成しません。
4. 保守を承認し、転送、実行、検証を観察します。再起動時の切断だけでは失敗と判断しません。
5. 同じホストへ再接続または状態更新し、成功結果、対象版、正常性を確認してからログイン、ファイル、ターミナルを試します。Client の新機能は Client を別途更新します。

## 3. 修復と証明書の保守

既存の識別子・ディレクトリを照合し、現在のインストールの修復を選びます。通常はデータと TLS を保持します。LAN 自己署名証明書の再生成または新証明書の提供を明示した場合だけ TLS 識別情報が変わります。証明書交換で再起動し、端末は新証明書を再確認・信頼する必要があります。名前には実際の LAN IP または DNS 名を含めます。

Windows 個人モードの保守は独立ヘルパー設定時に UAC を使い、状態更新だけでは要求しません。Linux システムの修復は root または sudo が必要です。追加ファイアウォール規則は対象ポートと範囲を確認します。ネットワーク到達不可だけで導入破損と判断しません。

## 4. 前のプログラムへロールバック

状態を更新し、前の版が記録されている場合だけ復元を選びます。記録がなければ操作できません。対象版、バックアップ、保守確認を済ませて実行し、結果、版、正常性を更新して再ログインします。

回退は記録済みディレクトリと対象版の配置エンジンを使います。過去の DB、構成、ファイル、コンテナボリュームは戻しません。新版が書いたデータを旧版で読めるか別途確認してください。

## 5. 削除とデータ保持

1. ホストと識別子を再確認し、クライアントを退出して必要なデータをバックアップします。
2. Server の削除を選びます。既定はデータ保持で、再導入や一時削除では保持します。
3. 永久削除が必要な場合だけ管理データ削除を選び、画面で求められるサーバー名を確認します。管理 DB、構成、鍵、ログが削除される場合があります。
4. 最終結果とホスト状態を更新し、未導入になったことを確認します。接続断だけでは削除成功を証明できません。
5. 保持したディレクトリを控え、再導入時に識別子とデータ位置を確認します。状態ファイル削除でアンインストールを偽装しません。Windows 個人モードは専用ヘルパーと関連ファイアウォール規則も削除します。

## 6. 操作履歴と失敗ログ

該当記録の操作 ID、操作、段階、状態、問題コードを読みます。デスクトップは選択操作をホストから更新して結果と配置ログを確認し、Android は記録の詳細から要約を開きます。失敗、中断、結果不明では元の操作を先に更新し、本機に成功が届かないだけで重複送信しません。

| 問題 | 確認順序 |
| --- | --- |
| 一時領域・クォータ不足 | 対象領域とクォータを確認し、操作 ID のログを保持してから容量確保 |
| 特権ヘルパー不可 | 状態と問題コードを読み、修復で復旧。日常 Server を高権限化しない |
| 削除エンジンがない | 版ごとの配置ファイルを確認して修復後に再試行。プログラム削除だけでは不十分 |
| TLS エラー・LAN 不通 | アドレス、名前、待ち受け、ファイアウォールを確認し、必要時に証明書修復を選択 |
| 結果と状態の不一致 | 操作 ID を保持してホスト結果を更新し、正常性確認前に成功としない |

共有前にアカウント、アドレス、パスワード、秘密鍵、トークン、ペアリングコード、機密パスを隠します。仮画像は撮影内容の指定であり、実機の受け入れ証拠ではありません。

## 日常保守の順序

導入状態と正常性、失敗操作を確認します。変更時は保守予定、バックアップ、確認を済ませて 1 回送信します。完了後に結果、版、正常性を確認し、ログイン、[ファイル](/docs/ja-JP/latest/apps/file-manager)、[ターミナル](/docs/ja-JP/latest/apps/terminal)、必要なホスト管理を試します。

## 独立コンポーネントサービスと保守の範囲

Windows の管理対象 Nginx、Mihomo、FRPC/FRPS は独立した SCM サービスを使用します。Linux の管理対象 FRPC/FRPS は独立した systemd サービスで、FRPC の設定ごとにインスタンスを分けます。Server、Guardian、Helper の停止やアンインストールだけでは保持したコンポーネントは停止しません。Server の再起動後はメモリ内の PID ではなく永続化した記録から管理状態を復元します。外部ランタイムには明示的な許可が必要で、自動的に管理対象サービスへ変換しません。

既定のアンインストールはコンポーネントの稼働、設定、所有権記録を保持し、元のデータ位置へ再インストールすると管理を再開できます。データの完全削除では、先に管理対象 SMB、Nginx、FRP、Mihomo を整理します。整理の失敗や所有権の競合時はプログラム、Helper、データを保持するため、失敗の操作記録を確認してください。連携したシステム Nginx、他のサイト、共有ファイルは所有権確認で保護されます。コンポーネントごとの保持・削除画面は未実装で、データルートを削除して稼働継続を期待することはできません。

隔離した Windows/Linux ホストでライフサイクル、OS 再起動、データ保持でのアンインストールと再インストールを検証済みです。GUI/API 全体とバージョン間更新の回帰確認は継続中です。[実装と検証](https://github.com/nanaminato/RelaxKonOS/blob/master/docs/services/RelaxKonOS.IndependentComponentServices.Progress.md)と[保守手順](/docs/ja-JP/latest/apps/server-maintenance)を参照してください。
