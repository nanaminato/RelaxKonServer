# コンポーネントセンター

コンポーネントセンター（Component Center）はホストコンポーネントの一元窓口です。「このサーバーの Nginx、Docker、Git、FRP、プロキシランタイム、Tailscale は誰が導入したのか、どのバージョンで、どこから来たのか」を答え、認可を得たうえで導入・更新・データを保持した削除を実行します。

業務設定は引き取りません。サイト、トンネル、コンテナ、購読、共有ディレクトリは従来どおり各アプリが管理します。

## コンポーネントとアプリの境界

| 関心事 | 担当 |
| --- | --- |
| コンポーネント本体、バージョン、入手元、導入の所有権とライフサイクル | コンポーネントセンター |
| サービスの起動・停止、業務設定、ログ、稼働診断 | 所属アプリ（Web サーバー、Docker、トンネル、プロキシ、ファイルサービスなど） |

アプリ側は各アプリの**設定 → コンポーネント依存**で現在の状態と移動先だけを示し、導入ボタンは提供しません。同じホストに互いを把握しない導入経路が二本できることを避けるためです。

## ページ

| ページ | 内容 |
| --- | --- |
| すべてのコンポーネント | ホストのプラットフォームで絞り込んだ一覧。分類・連携方式・入手元を含みます |
| 導入済み | ホストが存在を確認したコンポーネントとその所有権 |
| 更新可能 | 管理所有権が確認でき、かつ新しい版が確認できた場合のみ表示 |
| ワークロード | パッケージではなくコンポーネントを参照するアプリ環境（例：プロキシサーバーの基盤環境） |
| タスクと復旧 | バッチ下書き、凍結したタスク計画、実行進捗、復旧待ちの操作 |
| 入手元 | 各コンポーネントが現在のプラットフォームで宣言する入手元と、その接続状況 |

一覧には**現在のホストプラットフォームが対応を宣言している**コンポーネントだけが並びます。Windows ホストでは sing-box、Squid、Samba、Docker Engine は表示されません。検索・導入済み・更新可能も同じ判定を共有し、名前による例外はありません。

## コンポーネント一覧

| コンポーネント | 分類 | 対応プラットフォーム | 接続済みの入手元 |
| --- | --- | --- | --- |
| sing-box | ネットワーク | Linux | システムパッケージマネージャー（APT） |
| mihomo | ネットワーク | Linux、Windows | システムパッケージマネージャー（Linux）、信頼済みアーカイブ（Windows） |
| frpc / frps | ネットワーク | Linux、Windows | 信頼済みアーカイブ（クライアント／サーバーを別々に報告） |
| Nginx | サイトとリバースプロキシ | Linux、Windows | システムパッケージマネージャー（Linux）、信頼済みアーカイブ（Windows） |
| Squid | サイトとリバースプロキシ | Linux | システムパッケージマネージャー |
| Docker Engine | システム基盤 | Linux | システムパッケージマネージャー。公式ソースは未接続 |
| Git | システム基盤 | Linux、Windows | システムパッケージマネージャー（Linux）。Windows は既存 Git の観測のみ |
| Samba | ファイル共有 | Linux | システムパッケージマネージャー |
| Tailscale | ネットワーク | Linux、Windows | システムパッケージマネージャー（公式署名リポジトリ）、公式インストーラー（Windows MSI） |

「宣言」と「接続済み」は別物です。公式ソースが*計画中*と表示される場合、意図はあるもののこのビルドにトランザクションがない状態で、導入ボタンは表示されません。

## 導入の所有権

| 状態 | 意味 | 実行できる操作 |
| --- | --- | --- |
| 管理下 | RelaxKonOS が導入し、永続台帳に登録済み | 更新・修復・ロールバック・データを保持した削除（コンポーネントとプラットフォーム次第） |
| 外部導入 | ホストに既にあるが RelaxKonOS の導入ではない | 読み取りのみ。自動で引き取りません |
| 未接続 | 一覧にはあるが導入は所属アプリ側 | 説明と移動先のみ |
| 不明 | 読み取り失敗、権限不足、証拠不足 | 未導入ともみなさず、導入も提供しません |

Linux の外部システムパッケージは、**明示的に管理へ取り込む**ことができます。ただし dpkg の状態、プログラムファイルの帰属、`dpkg --verify`（設定ファイルの変更のみ許可）、サービスの帰属、`dpkg --audit` のすべてが成立する場合に限ります。一つでも失敗すれば状態は*不明*のままで、*未導入*へ格下げしません。取り込みはライフサイクルの認可を記録するだけで、**再導入も業務設定の引き取りもサービスの起動・停止の変更も行いません**。

管理下のパッケージが外部の apt で更新された場合、コンポーネントセンターは最初の認可を保持したまま「確認済みの外部変更」として提示しますが、新しい版を元の導入操作の成功応答として扱うことはありません。

## 変更の流れ

1. **状態の読み取り** — `GET /api/v1.0/components/{componentId}/state` で所有権、実測バージョン、導入方式、ホストのプラットフォーム、問題コード、未処理の操作を取得します。
2. **計画の凍結** — `POST /api/v1.0/components/{componentId}/plan` で入手元、バージョン（またはアーカイブの `releaseId`）、各成果物の URI・サイズ・SHA-256、データ保持の選択を固定します。
3. **確認と昇格** — 確認画面にホスト、操作、バージョン、入手元、ダイジェスト、関連成果物を並べ、この計画に対してホスト管理者の認可を一度だけ求めます。
4. **実行** — 計画はそのまま当該コンポーネントの導入台帳へ渡り、同じ冪等キー、権限、永続的な操作記録を再利用します。
5. **観測と復旧** — 進捗の確認、キャンセルの要求、元操作の照合を「タスクと復旧」で行います。

手順より制約のほうが重要です。

- 実行は**凍結した計画のみ**を使います。ホストのリビジョン、導入の同一性、対象バージョンが変われば計画は無効になり、再計画が必要です。
- 導入段階に入ったシステムパッケージは**パッケージマネージャーを強制終了してキャンセルできません**。
- 失敗や中断で**パッケージのバージョンを巻き戻しません**。現在のサービスが正常であることを元操作の成功根拠にもしません。記録は照合待ちとしてワークスペースに残ります。
- 削除は既定で業務データと設定を保持します。データ削除は別途選択し、別途確認する操作です。

## パッケージの入手元

Windows のアーカイブ導入とファイル導入には四つの入手元があり、いずれも同じ台帳へ渡されます。

| 入手元 | 内容 |
| --- | --- |
| サーバーがダウンロード | サーバーが承認済みの配布元から取得し、ダイジェストを照合します |
| クライアントがダウンロードしてアップロード | クライアントが送信します。参照は操作者に紐づき、期限切れになります |
| ローカルファイルから | ローカルのアーカイブを選び、そのファイルの実際のバージョンを入力します |
| サーバー上のファイルから | サーバー上の既存アーカイブを選び、ファイル参照を作成します |

「自分でダウンロードする」は選択した版の公式配布ページを開くだけです。取得したファイルは上記いずれかの経路で戻す必要があり、公式ページを開いたことで検証が緩むことはありません。

## 信頼できる入手元

- **システムパッケージ** — ホストが既に認可したリポジトリと署名メタデータを使い、候補と全依存成果物のファイル名、URI、バイト数、SHA-256 を凍結します。コンポーネントセンターが**リポジトリや署名鍵を自動で追加することはありません**。未登録の場合は専用のポリシー問題コードを返します。
- **信頼済みアーカイブ** — 設定に固定したバージョン一覧、または公式リリース一覧（Nginx、Mihomo、frpc/frps、Tailscale）を使います。結果は 15 分キャッシュし、手動更新できます。リダイレクト経由も手動ダウンロードも同じ規則に従います。
- **Tailscale（Linux）** — Tailscale Inc. の安定版署名リポジトリと鍵のフィンガープリントを明示的に確認する必要があり、ホストに既にある別の入手元や鍵を上書きしません。
- **Tailscale（Windows）** — 公式 stable のメタデータと SHA-256 を固定し、WinTrust の発行者、MSI の製品コード・アップグレードコード・アーキテクチャを確認してから導入トランザクションへ進みます。

固定バージョンは「設定上利用できる版」であり、上流の最新版ではありません。バージョン一覧や「最新です」という表示は安全性の結論ではありません。

## バージョン確認と更新

コンポーネントを選ぶとホスト状態を読み取り、バージョン情報を自動で準備します。導入済みの版と入手元が提示する版を表示し、いつでも再確認できます。

「更新可能」には、所有権が管理下として確認できること、入手元が本当に新しい版を持つこと、復旧待ちのトランザクションがないことのすべてが必要です。更新がない、状態が不明、トランザクションが未完了のいずれかであれば、更新できるとは表示しません。

Linux のシステムパッケージ更新は導入済みより高い版だけを受け付け、同一バージョンは更新とみなしません。更新と削除は frpc/frps のパッケージ全体を対象とし、更新後は業務側の入口からトンネルを起動し直す必要があります。削除ではアーカイブの対象を選びません。

## 起動時の依存チェック

アプリを開く前に、依存するコンポーネントの状態を読み取ります。結果は四種類です。

| 結果 | 扱い |
| --- | --- |
| 導入済み | そのまま開きます（サービス停止中でも導入済みとみなします） |
| 未導入 | コンポーネントセンターへの移動を案内します。移動しても自動導入はしません |
| 復旧待ち／実行中 | 先に「タスクと復旧」で処理し、その後アプリを開きます |
| 不明／権限なし | 未導入とみなさず、導入へ誘導もしません |

一つのアプリが複数のコンポーネントに関連する場合、それらは**代替**関係です。トンネルマネージャーは frpc と frps のどちらか一方が導入済みなら条件を満たします。ホストがそのプラットフォームで非対応と宣言している場合は「不要」となりアプリを開けます。プラットフォーム差を欠品と誤認しないためです。

## 権限とセキュリティ

- 読み取りには `server.components.read`、計画と送信には `server.components.manage` が必要です。
- 実行にはさらにホスト管理者の昇格が必要で、計画ごとに個別に認可します。昇格はキャッシュも再利用もしません。
- 特権実行は閉じたコンポーネント動詞のみを受け付け、汎用のコマンド実行入口はありません。
- 外部導入は自動で引き取りません。所有権は台帳と検証証拠から決まり、「公式らしく見える」ことからは決まりません。
- パッケージ変更、制御操作、サービス復旧は同じネイティブロックを共有し、未決または破損したパッケージ記録は新しい変更を止めます。

## 既知の制限

- 接続状況はコンポーネントとプラットフォームごとに異なります。Windows の Nginx アーカイブと Windows の Git は現時点でライフサイクルの片側しかなく、複数バージョンの更新・修復・ロールバックは所属アプリ側か未接続です。
- システムパッケージの導入、外部更新、中断復旧、`dpkg --verify` を含む全経路は、プラットフォームごとに実機での受け入れ確認が必要です。自動テストの通過はホストへの納品ではありません。
- バッチ下書きと凍結タスク計画は、バッチ経路を持つコンポーネント（現在は sing-box）に限られます。単一コンポーネントの導入は引き続き「タスクと復旧」以外のパネルが担当します。
- モバイル版は同じコンポーネント API を共有しますが、UI の規則は別途維持され、相互に验收を代替しません。
