# 証明書マネージャー

証明書マネージャーは現在のサーバーの証明書を管理します。RelaxKonOS が ACME クライアントとして申請・更新を行い、複数サーバーの調整やサーバー間の秘密鍵配布は行いません。

## 概要

三つの原則が全体の形を決めています。

1. **秘密鍵は常にこのホストで生成・保存**し、クライアントへ返しません。
2. **発行と配置は分離**します。証明書マネージャーは Nginx、IIS、リバースプロキシーの存在を知らず、配置は専用のデプロイヤーが担います。
3. **RelaxKonOS が 80 番ポートを常時占有する必要はありません。**

## 利用が適する場面

- サーバーが公衆網から到達でき、RelaxKonOS 自身の HTTPS 端点に信頼された証明書を使いたい。
- 既存の Web サーバーが 80 番を保持しているが、そのポートを奪わずに検証を完了したい。
- 毎年手作業で入れ替えるのではなく、証明書を自動更新したい。

## 現在の機能

- ACME v2 による発行。認証局はディレクトリ URL で設定し、特定の CA をハードコードしません。
- 検証方法：自動、HTTP-01（一時待ち受け／Web ルート）、DNS-01。一時待ち受けは 80 番が空いている間だけ使用し、チャレンジパスのみを処理し、発行完了・キャンセル・タイムアウト後に確実に解放します。
- Web ルート方式：チャレンジファイルを書き込んだ後に読み戻して検証し、検証終了後に清掃します。
- 証明書ストア：PEM を正規形式とするファイルストアで、Windows と Linux が同じモデルを使います。
- 鍵アルゴリズム：RSA と ECDSA。
- 配置先：RelaxKonOS 自身の HTTPS 端点（Kestrel）。
- 自動更新：ACME の更新情報（ARI）が示す推奨ウィンドウを優先し、証明書の有効期限をフォールバックとします。
- 管理画面は概要と証明書一覧で、申請、状態更新、証明書更新、失効、削除を提供します。サーバー HTTPS 証明書の変更は設定から行います。
- 申請ダイアログ：ドメイン、連絡先メール、検証種別、鍵アルゴリズム、公衆到達性の確認を、スクロール可能な内容領域へ事前検査結果と発行進捗とともにまとめます。

## サーバー HTTPS 証明書の変更

デスクトップでは **設定 → システム → サーバー HTTPS → サーバー HTTPS 証明書の変更** を使用します。証明書一覧の Kestrel への配置は廃止されています。変更には管理者認可と制限付きの特権実行を使用し、Server 全体を常時管理者として動作させる必要はありません。Windows のサービスモードと個人モードは証明書ディレクトリと ACL を個別に管理します。

選択したサーバー証明書は再起動後も復元され、他の証明書の自動更新で選択は変わりません。変更後は実際の接続先に対する証明書名と信頼状態を確認し、接続を再確認してください。証明書マネージャーは発行、更新、失効、削除を担当します。DNS-01 と他の Web Server への配置制限は後述のとおりです。

## 権限とセキュリティ

- 状態変更操作は能力と対象リソースごとに認可を確認します。サーバー HTTPS 証明書の変更には管理者認可を使用し、Server 全体の昇格を前提としません。認可不足時は安定した問題コードを返します。
- ホスト認可は統一管理者認証を使用します。システム認証済み管理者は資格を動的に確認し、一般ユーザーと Alias は選択した管理者を明示的に認証します。資格情報をログや任意 shell コマンドに入れません。導入権限と日常操作の認可は別で、[ログインとアカウント安全](/docs/ja-JP/latest/getting-started/login)を参照してください。
- **秘密鍵、アカウント鍵、CSR、CA の完全な応答は、API・ログ・監査・エラー詳細のいずれにも現れません。** 通常の API はドメイン、発行者、シリアル番号、有効期間、状態、サムプリント、更新状態のみを返します。
- 事前検査は構造化された結果を返します。ドメインの正規化と重複 SAN の検証、A / AAAA の解決、80 番の待ち受け権限と占有、ファイアウォールと上流プロキシー。事前検査は「公衆から到達可能」という結論を捏造しません。
- 長い処理には操作 ID と段階が返り、キャンセルや切断でもサーバー側の状態は失われません。

## プラットフォーム差

- 対象は **Ubuntu 24.04 LTS** と **Windows Server 2016 以降**です。
- Linux では秘密鍵ディレクトリをサービスアカウントのみに制限し、Windows ではファイルシステム ACL でサービスアカウントとシステムに限定します。
- 証明書の中核は Windows 証明書ストアに依存せず、一つのプラットフォームのストアが全体の依存になることを避けます。

## 既知の制限

- **対象プラットフォームでの受け入れが未完了**：中核と基本の管理画面は実装済みですが、実際の認証局、待ち受け挙動、ファイル権限の検証は対象ホストで別途実施する必要があります。
- **DNS-01 とワイルドカード証明書は未実装**で、後続段階です。したがって 80 番を一切公開できない環境では現在検証を完了できません。
- **Nginx、IIS、Apache への配置統合は未実装**で、現在の配置先は RelaxKonOS 自身の HTTPS 端点のみです。
- 80 番が空いていることは検証成功の保証ではありません。DNS、NAT、CDN、上流プロキシーの状態を判断できない場合、画面は管理者の確認が必要であると明示します。
