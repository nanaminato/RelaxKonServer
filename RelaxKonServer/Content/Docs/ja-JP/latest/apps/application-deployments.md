# アプリケーション配置

アプリケーション配置（Application Deployments）は **Docker マネージャーとは分離された**組み込みアプリです。Docker マネージャーがエンジンとコンテナーのプリミティブを扱うのに対し、アプリケーション配置は「アプリ」を長期存続する実体として公開・観察・復帰させます。

## 概要

配置対象は**希望状態**（どのリビジョンを、どの設定で、どのポートで動かすか）と**実際の状態**（エンジン内に実在するコンテナーとその準備完了結果）で構成されます。両者が食い違うと画面は「ドリフト」として表示し、その差異がコンテナー欠落、外部からの変更、未管理リソースのどれに由来するかを示します。

## 利用が適する場面

- チームがビルドしたイメージや成果物を、長期間稼働するホストに届けたい。手作業でサーバーにログインしてコマンドを打ちたくない。
- 過去のリビジョンを保持し、新版の準備完了チェックが失敗したときに一つ前に戻したい。
- ホストの Docker 資格情報をクライアントへ渡さずに、配置の進行とコンテナーのリアルタイムログを確認したい。

## 対応する取得元

| 取得元 | 説明 |
| --- | --- |
| コンテナーイメージ | イメージ参照とタグを指定し、サーバーがイメージ同一性を固定したうえでコンテナーを作成します |
| Java | JAR 成果物をアップロードし、エントリーポイントと引数をテンプレートで検証します |
| .NET | Web / Worker の publish 成果物をアップロードします。自己完結発行も選択できます |
| Python | 依存関係を固定したプロジェクトをアップロードし、ビルドはイメージ内で行います |

テンプレートはアーカイブの要否、イメージ参照の要否、自己完結発行の可否、既定のコンテナーポートを宣言するため、エントリーポイントと引数の検証は配置の前に行われます。

## 現在の機能

- 複数ステップのウィザードで、取得元・成果物・エントリーポイント・ポート・リソース・プロキシ経路を一つの流れで確認します。
- リビジョンと操作記録：公開のたびに不変のリビジョンを作成し、操作を追跡できます。
- 準備完了チェック：HTTP とプロセスの二段階。準備が整っていない候補がトラフィックを引き継ぐことはありません。
- バージョンロールバック：再ビルドせず、公開済みのリビジョンを再利用します。
- 配置中のリアルタイムログ配信。
- アップロード進捗：転送済みバイト数、割合、速度を表示し、キャンセルできます。
- イメージバージョン選択：レジストリで利用可能なタグから選択します。
- 任意のプロキシ経路：アプリごとにルートパス経路を一本追加し、保存前にサイト設定を検証します。

## 権限とセキュリティ

- 読み取りと変更は別々のポリシーで制御され、変更系の要求はホスト機能が有効であることを必要とします。
- 長い操作は冪等キーを伴うため、再試行が二度目の副作用を生むことはありません。
- 同一アプリの変更は相互排他、異なるアプリは並行可能です。
- 監査は実行者、対象、結果、操作 ID のみを記録し、資格情報は記録しません。
- シークレットはサーバーのデータ保護機構で暗号化して保存し、API はバージョン番号のみを返します。
- アップロードはエントリー数、展開後の総量、パス境界で検証し、範囲外パスとシンボリックリンクを拒否します。

## プラットフォーム差

配置対象は **Docker Engine が動作するホスト**であるため、主に Linux サーバー向けです。Windows 側はクライアントと開発環境に適します。

## 既知の制限

> **現在の状態：実装済み・未検証。** すべての実装項目はコンパイルと静的検証を通過していますが、実行時の挙動は実在の Docker Engine で受け入れられていないため、本ページを「本番利用可能」と読むべきではありません。

- **実エンジンでの受け入れが未完了**：イメージ取得、ビルド、作成、準備完了、ロールバック、障害注入は Docker のあるホストで未実行です。
- **単一サービス Compose プロジェクトの配置は未実装**：配置はコンテナーのプリミティブで表現するため、ウィザードから Compose プロジェクトをそのまま投入することはできません。
- **全体の割合は約束しません**：ビルド段階は段階内の作業量から進捗を報告し、信頼できる分母がない場合は数値をでっち上げず不明として表示します。
- 継続的インテグレーションの代替ではありません。ソースビルド、リポジトリフック、パイプライン定義はありません。
