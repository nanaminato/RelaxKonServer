# プロトコルと通信

クライアントとサーバーは**明示的なプロトコル**を通じて通信します。業務コードが生の HTTP や WebSocket を直接呼び出すことはなく、すべてのやり取りはコントラクトを経由します。

## コントラクトに含まれるもの

| 要素 | 目的 |
| --- | --- |
| DTO | 安定したシリアライズのための `[JsonPropertyName]` 付き `sealed record` |
| ルート定数 | `*ApiRoutes` により文字列リテラルの散在を排除 |
| ハブインターフェース | 強い型付けのクライアントインターフェースと Methods / Events 定数 |
| シリアライズ規約 | 一貫した命名ポリシーと型マッピング |

## 2 つのトランスポート

### REST

リクエスト／レスポンス型の操作に使用します。ワークスペース設定、ファイル操作、Docker、証明書、Git などです。エンドポイントは `/api/v1.0/*` 配下にあります。

### SignalR

継続的なプッシュと双方向ストリームに使用します。

| ハブ | 目的 |
| --- | --- |
| `/hubs/terminals` | ターミナル PTY のバイトストリーム |
| `/hubs/performance` | 1 Hz のパフォーマンスメトリクス |
| `/hubs/guardian-logs` | Guardian ログの配信 |
| `/hubs/workspace` | ワークスペース状態のイベント |

## SignalR を選ぶ理由

- 自動再接続
- `AccessTokenProvider` による組み込みの JWT 認証
- 強い型付けのハブコントラクト
- 生の WebSocket エンドポイントを別途維持する必要がない

## ルール

- 境界をまたぐ通信はすべてプロトコルアセンブリを経由します
- プロトコルアセンブリはサードパーティ依存を持ちません
- クライアントプロキシはクライアントに、ハブとエンドポイントはサーバーに置きます
